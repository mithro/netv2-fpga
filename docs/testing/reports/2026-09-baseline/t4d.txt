=== notes
Date: 2026-09-05.

`debug t4i` was sent to enable the TERC4 interrupt in the running firmware.
Per legacy/firmware/ci.c (~line 1141), this is a live-firmware-state change:
it sets hdmi_in0_decode_terc4_ev_enable/pending and adds
HDMI_IN0_INTERRUPT to the CPU's interrupt mask. It is volatile CPU/CSR
state, not something written to flash: it persists only until the FPGA is
reconfigured (a JTAG reload), which the golden unit is never subjected to
outside of that mechanism. It does not survive a power cycle or CPU reset.

The `hdmi0 terc4 packet cnt` / `char cnt` line that `debug t4d` prints is
mislabeled in the source: per legacy/firmware/ci.c:1155-1156, that first
printf actually reads hdmi_in1_decode_terc4_t4d_count /
_t4d_char (input1's TERC4 decoder), while the five bch0..bch4 words that
follow (ci.c:1156-1164) read hdmi_in0's TERC4 capture registers. So the
printed "hdmi0" prefix on the packet/char-count line is misleading: those
counts belong to input1 (the MagicMirror/overlay input from the Pi Zero
running the compositor UI, which is a plain framebuffer output and is not
expected to carry HDMI data islands / TERC4-coded audio packets), while
input0 (the rpiz-3 HDMI source under test, feeding the capture-card output
path) is what the five BCH words characterize.

Reading of the numbers: **neither the packet/char counters nor the BCH
words could be obtained in this run.** Both `debug t4i` and both `debug
t4d` calls returned the same 4-line help_debug() fallback text (the exact
text of legacy/firmware/ci.c's help_debug(), reached only via its `else`
branch when the token doesn't match any recognized `debug` subcommand — see
ci.c line ~1170), not the interrupt-mask/terc4_ev_enable print or the
packet-count/BCH lines specified at ci.c:1154-1164. This is reproducible
(both debug t4d calls returned byte-for-byte identical output), so it is
not attributable to serial contention on this corrected run (mm was
confirmed paused correctly this time, unlike the first, contaminated
attempt above).

The most likely explanation: **the bitstream/firmware image currently
loaded on rpi3-netv2's FPGA predates the t4i/t4d additions visible in this
repo's legacy/firmware/ci.c**, i.e. the running image's do_debug() simply
has no "t4i"/"t4d" branches to match, so control falls through to
help_debug(). This cannot be distinguished from a token-parsing bug from
the console alone without reflashing (out of scope/forbidden for this
golden unit), but help_debug()'s hard-coded 4-line text matching exactly
what came back for both t4i and t4d is strong evidence for "unrecognized
subcommand", not a garbled read.

Net effect for phase 1: no islands-arriving-on-input1 vs.
islands-arriving-on-input0 comparison could be made this run, because the
firmware currently on the golden unit does not expose the counters needed
to make it. This is itself a useful phase 1 finding: any phase 7a
diagnostic that wants live TERC4 packet/BCH counters will need a firmware
image that includes the ci.c t4i/t4d handlers, built and loaded
deliberately (and knowingly, since that changes the unit away from "stock,
never modified").

Separately, `status` reported input0 at 1920x1080 resolution (satisfying
the expected check) but at "0. 0 MHz", while input1 reported 148.49 MHz —
the inverse of the MHz split recorded earlier the same day in
tests/hdmi-suite/README.md ("input0: 1920x1080 (@ 148.49 MHz)"). This may
simply reflect a momentarily unlocked/mid-negotiation input0 clock at the
instant of this read (other agents/tests may have been exercising the same
shared rig concurrently), or a real change in what's connected to which
input; it was not chased further here since it stayed outside this task's
scope (t4i/t4d + EDID + rpiz-3 ELD), but it is worth a follow-up look in
phase 7a if the input0/input1 MHz split keeps flipping.
